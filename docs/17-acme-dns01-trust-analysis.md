# NoDNS: Let's Encrypt ACME DNS-01 — Trust Model & Feasibility Analysis

> **Status**: Research synthesis. Decision needed before implementation.
> **Date**: 2026-06-07
> **Related**: [docs/16-crypto-key-cert-patterns.md](16-crypto-key-cert-patterns.md) (Option E deep dive)

## The Core Question

Can we use Let's Encrypt ACME DNS-01 to give NoDNS users **browser-trusted HTTPS certificates**, where trust is anchored from the npub identity through DNS to the CA?

**Short answer: Yes, and it's the most impressive demo we can build.**

---

## Trust Chain Analysis

```
Layer 1: Nostr Identity
  User's nsec signs kind:11111 event → proves npub owns the subdomain

Layer 2: DNS Control (DNSSEC-authenticated)
  Bot publishes _acme-challenge.npub1xxx.nodns.shop TXT → Knot DNS signs it (ECDSAP256SHA256)
  DNSSEC chain: Root → .shop → nodns.shop → _acme-challenge TXT

Layer 3: WebPKI (browser-trusted)
  Let's Encrypt verifies DNS-01 challenge → issues certificate
  Browser validates: LE root → intermediate → end-entity cert → green lock
```

### Full Trust Flow

```
1. User publishes Nostr event: "I want HTTPS for my subdomain"
   Trust: Nostr signature (Schnorr) proves npub identity

2. Bot verifies event signature → confirms npub owns npub1xxx.nodns.shop
   Trust: Bot validates event + checks authority (same as all record processing)

3. Bot creates ACME order with Let's Encrypt
   Trust: Bot holds ACME account key (separate from user's nsec)

4. Bot receives DNS-01 challenge token
   Trust: Challenge token is random, generated by LE

5. Bot publishes _acme-challenge.npub1xxx.nodns.shop TXT via DDNS UPDATE (TSIG-signed)
   Trust: Same mechanism as all DNS record updates

6. Let's Encrypt queries DNS → gets DNSSEC-validated TXT record → challenge satisfied
   Trust: DNSSEC chain validated by LE's resolver

7. Let's Encrypt issues X.509 certificate for npub1xxx.nodns.shop
   Trust: CA signature (LE → ISRG Root X1 → browser trust store)

8. User installs cert on their server → browser shows green lock
   Trust: Full chain verified by browser
```

### Where Trust Anchors Live

| Trust Anchor | Who Trusts It | What It Proves |
|---|---|---|
| **nsec/npub** (secp256k1) | Nostr network | "I am the owner of this subdomain" |
| **DNSSEC** (ECDSAP256SHA256) | DNS resolvers | "This TXT record is authentic" |
| **TSIG** (HMAC-SHA256) | Knot DNS | "The bot is authorized to update DNS" |
| **Let's Encrypt** (ISRG Root X1) | Browsers | "This domain's identity is verified" |

### Trust Gap Analysis

The user raised a critical point: **either the CA or Let's Encrypt could in theory not respect the NoDNS consensus rules.**

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| LE refuses to issue for npub subdomains | Low | No cert issued | Test with staging first; fallback to self-signed |
| LE rate-limits (50/week for nodns.shop) | Medium | Some users can't get certs | ARI renewals exempt; use staging for dev |
| LE revokes certificate | Very Low | Cert stops working | Re-issue; self-signed fallback |
| LE changes policy against DNS-as-a-service | Low | All certs affected | DANE/TLSA as backup (Option B) |
| DNSSEC misconfiguration breaks challenge | Low | Challenge fails | Monitor DNSSEC health |
| Bot compromises ACME account key | Low | Unauthorized cert issuance | Protect key; audit logs |

**Key insight**: The ACME DNS-01 challenge only proves **DNS control**, not **Nostr identity**. LE doesn't know or care about Nostr. But the DNS record was only published because the npub holder signed a Nostr event — so the trust chain is implicit: npub → Nostr event → bot → DNS → LE → browser.

## Technical Implementation

### Recommended Library: `instant-acme`

| Library | Verdict |
|---|---|
| **`instant-acme`** | ✅ **Best fit.** Pure Rust, DNS-01 support, ARI, production-used. Active (v0.8.x, 2025-2026). |
| `acme2` | ❌ Stale. Last release 2022. OpenSSL-based. |
| `rustls-acme` | ❌ Wrong shape. TLS server helper, not DNS-01 client. |
| `acmex` / `certon` | ⚠️ Not audited in depth. |

Source: [instant-acme on GitHub](https://github.com/djc/instant-acme) — README features, `provision.rs` example.

### ACME DNS-01 Challenge Mechanics

**TXT record content**: `base64url(SHA256(token + "." + JWK_thumbprint))`
**TXT record location**: `_acme-challenge.npub1xxx.nodns.shop`
**TTL**: 60-300 seconds recommended
**Cleanup**: Delete after validation succeeds
**Propagation**: LE may wait up to ~1 hour (usually seconds with authoritative DNS)

### Rate Limits

| Limit | Value | Scope |
|---|---|---|
| Certificates per registered domain | 50/week | All of nodns.shop |
| Certificates per exact FQDN set | 5/week | Per subdomain |
| Renewals (ARI-based) | Exempt | — |
| Failed validations | 5/hour | Per account |
| Accounts per IP | 10/3hrs | Per IP |

**Staging environment**: `https://acme-staging-v02.api.letsencrypt.org/directory` — higher limits, untrusted root.

### Certificate Lifecycle

- **Validity**: 90 days (LE standard)
- **Renewal**: Recommended at ~60 days; ARI automates this
- **Key management**: User can generate CSR + key (bot never sees private key), OR bot generates and returns PEM
- **Account key**: Separate from cert key; bot stores ACME account credentials

### Bot Architecture Integration Points

| Component | File | What to Add |
|---|---|---|
| **Config** | `config.rs` | `[acme]` section (enabled, server_url, contact_email) |
| **Event parsing** | `parser.rs` | Parse `["acme", "request"]` tag |
| **Event processing** | `main.rs` | ACME order flow in `process_nostr_event` |
| **DNS update** | `dns.rs` | Reuse `Updater::update_record()` for `_acme-challenge` TXT |
| **Persistence** | `store.rs` | `acme_orders` table (id, domain, status, cert, expires) |
| **API** | `main.rs` | `/api/acme/order` (POST), `/api/acme/cert/{id}` (GET) |
| **State** | `main.rs` | `acme: Arc<AcmeService>` in AppState |

### Concrete Implementation Flow

```
1. User clicks "Get HTTPS Certificate" in frontend
2. Frontend: generate RSA/ECDSA keypair + CSR in browser
3. Frontend: publish Nostr event with ["acme", "request"] tag + CSR in content
4. Bot: verify event signature + authority
5. Bot: create ACME order via instant-acme
6. Bot: receive DNS-01 challenge
7. Bot: publish _acme-challenge TXT via DDNS UPDATE (reuses existing dns.rs)
8. Bot: tell LE to verify
9. LE: queries DNS → validates DNSSEC → challenge satisfied
10. Bot: finalize order with user's CSR
11. Bot: receive certificate
12. Bot: store cert + notify user via API
13. Frontend: download cert (PEM) + private key (user's own)
14. User: install cert on their server → browser shows green lock
```

**Alternative (simpler demo)**: Bot generates keypair + CSR, returns both cert and key. User just downloads and installs. Less secure (bot sees private key) but much simpler for demo.

## Demo Strategy

### Why This Is the Most Impressive Demo

1. **"Your Nostr identity just got a browser-trusted HTTPS certificate"** — one sentence, huge impact
2. Shows the full trust chain: Nostr → DNS → DNSSEC → ACME → Browser
3. Green lock in browser = immediately verifiable by anyone
4. No custom software needed — just a browser
5. No other decentralized DNS system does this (ENS: gateway certs, Handshake: requires DANE support)

### Demo Flow (60 seconds)

```
1. Visit nodns.shop
2. Click "Try it in 5 seconds" → TXT record published
3. Click "Get HTTPS Certificate" → ACME flow starts
4. Wait ~10-30 seconds for LE verification
5. Download cert + key
6. Show: cert installed on a test server → green lock in browser
```

### Staging vs Production

- **For demo**: Use Let's Encrypt **production** (real certs, browser-trusted)
- **For development**: Use **staging** (fake certs, no rate limit impact)
- Rate limit concern: 50 certs/week is fine for a demo. Even 10 demo runs/day = 70/week, which is slightly over — but we can reuse certs for repeated subdomains (5/week per exact FQDN).

## Comparison with Other Options

| | Option B (SLIP-10 + TXT) | Option E (ACME DNS-01) | Combined B + E |
|---|---|---|---|
| **Browser trust** | ❌ | ✅ Green lock | ✅ |
| **Nostr↔TLS link** | ✅ Mathematical (SLIP-10) | ❌ Implicit (via DNS) | ✅ Explicit + implicit |
| **Demo impact** | "Cool crypto" | "It just works in my browser" | Both |
| **Implementation** | ~300 lines frontend | ~500 lines bot | ~600 lines total |
| **Dependencies** | @noble/hashes, @peculiar/x509 | instant-acme crate | Both |
| **Maintenance** | Low (no renewal) | Medium (90-day renewal) | Medium |

### Recommended Path: Option E First, Then Add B

1. **Phase 1**: ACME DNS-01 (Option E) — maximum demo impact, browser-trusted certs
2. **Phase 2**: Add SLIP-10 attestation (Option I) — Nostr↔TLS cryptographic link as bonus
3. **Result**: Combined approach — browser-trusted certs WITH mathematical Nostr link
